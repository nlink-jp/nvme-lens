# 既定閾値の根拠となる実測ベースライン

> 測定: 2026-08-17 08:46 〜 2026-08-18 08:22（23.6 時間、1 分間隔、欠測なし）
> 対象: Mac Studio (M2 Max) / macOS 26 / nvme-lens v0.1.2

既定閾値がどこから来たかを記録する。「なぜ 78℃ なのか」に後から答えられる材料であり、
同時に**将来の比較基準**でもある。同じドライブが後日ここより高く張り付いていれば、それは
設置環境か筐体か、ドライブ自身に何か起きたということになる。

## 収集の完全性

3 台とも **1443 サンプル / 23.6 時間、欠測ゼロ**。1 分間隔の期待値どおり。

これは App Nap 対策（`ProcessInfo.beginActivity`）が機能していることの実証でもある。
これが無ければ、バックグラウンド専用アプリのタイマーは夜間に凍結し、履歴に穴が空く。
穴は「アプリが動いていなかった」としか読めず、後から埋める手段はない。

## 温度

| ドライブ | 接続 | min | max | 平均 | 78℃ 超 | 83℃ 超 |
|---|---|---|---|---|---|---|
| APPLE SSD AP1024Z | Apple Fabric（内蔵） | 35 | 44 | 37.9 | 0 分 | 0 分 |
| CT1000P1SSD8 | PCI-Express（TB4 外付け） | 51 | 54 | 52.4 | 0 分 | 0 分 |
| WD_BLACK SN770 1TB | PCI-Express（TB4 外付け） | 67 | 71 | 68.7 | 0 分 | 0 分 |

最も高温の SN770 のパーセンタイル: **p50 = 69℃ / p90 = 70℃ / p99 = 71℃**。

### 既定 78℃ / 危険 83℃ を維持する理由

- **アイドル定常が 69℃、24 時間の最大が 71℃。閾値まで 7℃ の余裕**がある
- 別途の負荷試験（`dd` による約 5 分の連続読み出し）で **82℃** まで上昇することを実測済み。
  つまり閾値 78℃ は「実際に熱くなったとき」を捕まえる位置にある
- これ以上下げると通常運用で鳴り始める。SN770 のようなアイドル 69℃ のドライブでは、
  70℃ 付近の閾値は**鳴りっぱなしになり、結果として誰も有効にしておかない**
- 上げると 82℃ 級の実際の過熱を見逃す

p99（71℃）と警告（78℃）の間に 7℃、警告と実測ピーク（82℃）の間に 4℃。誤検知と検出力の
配分としてこの位置が妥当と判断する。

### 持続時間 5 分について

温度は瞬間値では判定しない。ファイルコピー中の一時的なピークで鳴らすと、鳴っても何も
できない通知が増えるだけである。上記の負荷試験では 82℃ に達するまで約 4 分かかっており、
5 分という条件は「実際に持続する加熱」と「一時的なピーク」をこの実測どおりに分ける。

## 電源断レート

| | 旧 USB 筐体（RTL9210B-CG） | 現行 TB4 筐体（ASM2464PD） |
|---|---|---|
| 電源断レート | **7.3 回/時** | **0 回/時**（23 時間通電、増分 0） |
| Unsafe Shutdowns | 累計 72 回 | 増分 0 |

旧筐体は `pmset disksleep`（既定 10 分）のたびにドライブを電源断させていた。当機は
`pmset sleep 0`（sharingd / powerd が抑止）でシステムスリープしないため、この電源断は
スリープ由来ではなくアイドル suspend 由来と確定している。

既定閾値 **2.0 回/時** に対し実測 0。誤検知しない。そして旧筐体の 7.3 回/時 は明確に
超過するので、同種の問題があれば検出できる。**この閾値だけは、検出側も実データで
裏付けが取れている。**

## 検証できていないこと

**寿命指標は 24 時間ではまったく動かない。**

| 指標 | 24 時間の変化 |
|---|---|
| Percentage Used | 3 → 3 / 3 → 3 / 0 → 0（変化なし） |
| Available Spare | 100 → 100（全台変化なし） |
| Media Errors | 増分 0（全台） |

したがって以下の 3 つの閾値は、**誤検知しないことは確認できたが、検出できることは
確認できていない**。

- 使用率 80% で警告
- Available Spare がドライブ自身の閾値に近づいたとき（枯渇が始まってから）
- メディアエラーの増分

これは実装の不足ではなく、**劣化が始まるまで原理的に確認できない**。単体テストでは
合成した値で判定ロジックを検証してあるが、実データによる裏付けは存在しない。ここを
「検証済み」と読まないこと。

## 副次的に確認できたこと

- 内蔵 SSD は 24 時間で **通電 +3 時間**（実時間 23.6h に対して）。省電力状態に入っている
  時間が長い。外付け 2 台は +23 時間で実時間とほぼ一致する
- 内蔵の書き込みは 24 時間で約 **80 GB**。外付け 2 台は 0（この期間はアイドル）

## 再測定の手順

```sh
sqlite3 ~/Library/Application\\ Support/nvme-lens/history.sqlite "
SELECT d.model, COUNT(*), MIN(t.hotspot_c), MAX(t.hotspot_c), ROUND(AVG(t.hotspot_c),1)
FROM temperature_samples t JOIN drives d ON d.serial=t.serial GROUP BY t.serial;"
```

GUI からは History ウィンドウで同じことが見える（レンジ 24 hours、指標を切り替え）。
